# 代码结构与技术债审查：详细规划

日期：2026-10-01。状态：阶段0—2首轮审查已完成；阶段3—6与整改清理尚未完成。详见 [首轮审查报告](2026-10-01%20%E4%BB%A3%E7%A0%81%E7%BB%93%E6%9E%84%E4%B8%8E%E6%8A%80%E6%9C%AF%E5%80%BA%E9%A6%96%E8%BD%AE%E5%AE%A1%E6%9F%A5%E6%8A%A5%E5%91%8A.md)。

本文件由原「审查框架」扩展，是下一位执行者的工作说明。目标是让现有代码更清楚、更统一、更容易安全修改，保持已经认可的功能和风格。先以证据确认问题，再逐批调整；不做一次性重写。

## 一、任务与完成边界

Task：审查历史残留、重复规则、职责混杂、类型与参数、数据权威及生命周期，形成可执行整改清单。
Task type：工程结构审查；后续整改为独立小任务。
User scenario：持续迭代阅读、笔记和统计时，能够找到唯一实现入口，不因清理破坏已有数据、路径跟随或跨界面一致性。
Current behavior：现有服务与纯逻辑模块已建立；大型界面、历史迁移与覆盖样式仍需系统核查。
Reproduction：通过调用链、配置、测试及隔离实机闭环确认；搜索结果不能独立证明废代码。
Root-cause evidence：首轮报告记录源码证据与一项纯内存完整事务复现；其他候选仍须定向验证，不宣称全部根因或完整审查已完成。
Target behavior：每项规则有明确归属、每个字段有唯一权威来源，确认无用的代码可删除，必要兼容有保留依据。
Completion criteria：交付模块图、问题清单、清理候选、参数字典、覆盖矩阵与分批任务；实施后逐项提供验收证据。
Scope：src、styles.css、测试、类型与构建配置、打包及管理文档的一致性。
Explicitly excluded：新功能、新视觉方案、依赖升级、重新设计数据格式、全面格式化、日常库修改、提交推送与发布。
Affected data and files：调查阶段只读取必要源码与配置，不读取或导出整本书、密钥或用户笔记正文；整改范围逐批列明。
Automated verification：调查做定向静态检查；实现按项目规定 npm run verify，并补充有意义的行为测试。
Obsidian verification：按实际改动选取下文闭环，不用自动测试替代实机验收。
Failure handling：证据不足保留并标记待确认；数据安全或启动故障另立修复任务，暂停相关清理。
Rollback：每批保留独立来源差异与对应构建；涉及迁移另定义数据恢复方式，代码回退不等于数据回退。
Documents to update：本规划状态、审查报告、整改任务、03改动日志、04接续说明；长期规则有变化才改01。

## 三、审查顺序与阶段交付

### 阶段0：冻结范围与建立基线

1. 按项目要求读取00、01、04，再核对02优先级、Git状态、版本和构建脚本。
2. 列出已提交基线、当前未提交内容、用户修改与本任务改动；不要stash、reset或批量格式化。
3. 核对测试脚本、严格编译范围、生成产物、发布排除项；不执行deploy:local或sync:management。
4. 实施前运行verify并记录既有失败。只读调查不必为了数量重复构建。

交付：基线表与范围说明。退出条件：工作区归属、验证方式、数据禁区明确。

### 阶段1：画模块图与数据流，优先主工作流

按以下顺序追踪实际调用，而不是按文件顺序浏览全仓库：

| 用户动作 | 主要调查入口 | 必须追到的终点 |
| --- | --- | --- |
| 打开EPUB、恢复位置、保存书签 | main、EpubView、EpubReader、book-state-service | data.json保存队列与关闭／重载 |
| 高亮、追加／编辑／删除笔记和关联 | EpubReader、EpubView、book-note-operations、highlight-service、highlight-transaction-service | Markdown、索引、事务失败及恢复 |
| 侧栏与卡片显示 | sidebar、book-note-projection、book-note-service、book-note-document | 相同解析片段与缓存刷新 |
| 提升知识笔记、返回来源 | knowledge-note-service、knowledge-note-store、reading-source-link、global-markdown | 稳定来源身份、已有文件查找与跳转 |
| 书籍／笔记改名移动 | main rename入口、book-path-service、book-note-service | 队列、路径别名、索引及打开中的视图 |
| 查词、翻译、手动收藏 | translation、word-assets、word-asset-service、词卡入口 | 离线结果与外部请求边界、word-assets索引 |
| 封面、删除书籍、补录与统计 | LibraryApp、cover-cache-service、reading-stats-service | 文件操作、统计状态、失败提示与保留数据 |

交付：一张实际模块依赖图、每个核心用例一条调用链、数据读写表。标注界面、服务、领域、存储、外部适配。图中尚未追踪的边标为“待确认”，不画理想架构冒充现状。

### 阶段2：审查数据权威、并发与失败路径

优先查风险最高的写入链路，再做普通代码清理：

- Markdown内容与定位索引是否分工明确；缓存／摘要是否可能反向覆盖正文。
- 界面直接写入是完整服务入口还是绕过事务；先画调用关系，再提出移动职责的方案。
- 创建、更新、删除、路径跟随是否进入正确队列；异步返回是否可能覆盖切书后的状态。
- Markdown写入失败、索引提交失败、重载恢复、损坏索引和过期缓存是否按既有保护处理。
- 删除一条笔记是否保留原文与其他笔记；删除书籍是否保留Markdown和知识笔记。
- 路径改名移动是否与保存竞争；来源链接、别名、缓存键和视图是否使用一致身份。

交付：按字段列明唯一权威来源、写入入口、队列／事务、失败结果与恢复路径。已存在测试先复用；发现缺口才补针对性测试。真正的数据缺陷优先独立修复，不夹在重构中。

### 阶段3：历史残留与重复逻辑

每个候选必须回答：谁注册它、谁调用它、是否动态引用、是否处理旧数据、是否参与打包或恢复。

分类：

| 类别 | 处理方式 |
| --- | --- |
| 已确认无运行、构建或兼容用途 | 可进入最小删除批次，说明证据和影响范围 |
| 搜索不到直接调用，但动态用途不明 | 保留待确认，继续查命令、事件、字符串、DOM选择器与测试 |
| 迁移、备份、事务恢复、历史链接兼容 | 单独记录保留原因与未来退出条件，不按废代码删除 |
| 确实重复且行为等价 | 优先复用现有模块；记录默认值、错误、时序差异再合并 |
| 看起来相似但语义不同 | 保留差异，例如临时翻译与保存词卡、摘要与完整笔记 |

重点候选：已退出详情页／复习／独立词条界面的入口和样式、旧设置字段、重复解析、路径标准化、读取兜底、菜单与图标工具。旧PDF命名或旧提取注释只能作为线索，不能仅因名称陈旧删除。

交付：清理候选表与重复规则对照表。禁止以零引用搜索、未被测试执行或名字像旧功能作为唯一删除依据。

### 阶段4：类型、命名、参数与默认值

建立概念字典，每项记录：含义、类型、单位、有效范围、默认值、空值／缺失语义、读写入口、权威来源、是否持久化或对外暴露。

优先核对：bookPath／notePath／来源路径、片段id／blockId、CFI、进度比例与百分比、阅读时长单位、日期与系统时间、reader设置、词条与短语类型、封面缓存键、索引可用状态。

规则：

- 内部局部命名可在单一调用闭环中统一；持久化字段、Markdown元数据、命令ID、链接协议必须另作兼容评估。
- 不把词间距、字间距、行距等不同单位统成同一个参数；不猜测数值是秒还是毫秒。
- 排查any、类型断言、重复类型及宽泛对象；从共享边界开始收紧，不用as unknown as或关闭检查掩盖问题。
- 按模块逐步扩展严格检查，记录files和import实际纳入范围；不一次打开全仓strict后大规模补断言。
- 默认值、归一化与校验应有明确唯一入口；显示格式可以不同，不能反向改变存储语义。

交付：概念／参数字典、类型覆盖表、需要迁移的字段清单。没有确认类型或单位的项写“待追踪”。

### 阶段5：模块职责、生命周期与生态边界

只有在前面调用链明确后，才决定拆分：

- EpubReader：区分阅读呈现、选文动作、笔记编辑、词卡、外部调用和DOM订阅；优先搬出独立纯规则与完整用例，不按每个按钮建文件。
- LibraryApp：区分书架投影、书籍管理用例和统计呈现；首先移出确认绕过服务的文件操作，保留当前视觉和交互。
- EpubView与main：核对React挂载、事件注册、保存队列、统计计时与主题同步的所有权；避免启动入口成为补丁集合。
- 事件／观察器／定时器：建立注册、释放、切书、关闭、卸载、异步返回的配对表；确认不会重复监听或写入已关闭视图。
- 私有第三方对象、DOM选择器、模拟点击：留在适配边界，失败不进入核心持久化链路。
- 不建立没有明确职责的“通用管理器”；不为缩短文件引入大量跨模块回调或循环依赖。

交付：当前职责表、生命周期表、候选拆分图。每个新边界须解释它减少了哪一种实际耦合。

### 阶段6：样式、构建与文档一致性

- 将样式规则对应到实际组件、状态、深浅模式和媒体条件；结合计算样式判断覆盖顺序。
- 合并前比较特异性、important、顺序、内联样式与窄屏规则；废样式删除不能导致已认可的卡片间距回退。
- 保留主题背景与字号约定，不能把代码梳理变成新一轮视觉重设计。
- main.js只由构建生成；内置词典、许可、发布附件和用户数据排除规则必须保留。
- 核对最低宿主版本与实际所用API／浏览器能力，但未证实兼容问题前不改版本声明。
- 总览、规则、接续说明出现旧页面或旧版本时，区分过时当前描述和有效历史记录；修正当前入口，不抹去历史证据。

交付：样式所有权表、构建来源表、文档冲突清单及修正建议。

## 四、问题清单与优先级

每项使用固定记录：

| 字段 | 要求 |
| --- | --- |
| 编号／状态 | 待确认、已确认、计划实施、已实现待验、已验收、暂缓 |
| 位置／触发场景 | 文件、函数或选择器；用户如何触发 |
| 证据 | 调用链、样例、测试或实机结果；区分事实与推断 |
| 问题与影响 | 数据风险、功能错误或维护成本，不能只写“不优雅” |
| 最小方案／保留理由 | 复用何处、删除何物、为何必须保留 |
| 依赖与风险 | 涉及身份、数据、第三方、时序和已有改动 |
| 验证／回滚 | 自动测试、实机场景、可恢复边界 |
| 完成条件 | 可检查的结果，不以改了多少行或通过多少测试代替 |

P0：已确认的数据损坏、启动失败或保存破坏。立即独立诊断修复。
P1：主流程错误、数据权威冲突、明显生命周期泄漏及高风险耦合。
P2：等价重复、内部类型／默认值分散、可证实的职责混杂。
P3：无行为影响的命名、注释和少量整理。仅在对应模块任务中处理，不开全仓格式化。

“文件很大”和“any很多”本身不构成P0／P1；优先级依赖实际影响。

## 五、实施批次与放行条件

首轮只交付审查报告，不能把本规划直接当成已确认删除清单。审查完成后按风险决定顺序：

| 批次 | 范围 | 放行条件 |
| --- | --- | --- |
| A：确定残留 | 少量确认无用入口、函数或样式 | 动态用途和升级需求排除，完整验证与相关实机无回归 |
| B：规则与类型 | 一项等价重复、内部参数或共享边界类型 | 行为差异表完成，存储语义不变，相关测试和严格检查通过 |
| C：用例边界 | 一个完整用例归入既有服务 | 写入顺序、异常、通知和调用方全部覆盖，不能只移动代码 |
| D：组件职责 | 一个独立呈现或生命周期职责 | 依赖变少且无循环，切书／关闭／重载实机通过 |
| E：样式归属 | 一个组件的重复覆盖收敛 | 浅／深、正常／窄、长内容和主题字号的实际效果保持 |
| 独立专项 | 数据迁移、兼容删除、第三方协议变化 | 另有生命周期、失败恢复、升级与回退方案，不能夹带普通清理 |

每批只解决一类可验收问题；出现无关差异或连续难以定位的回归立即缩小范围。顺序不是硬性先删除：有数据风险时先修安全问题。提交、推送、发布需要单独授权，规划不自动授权。

## 六、验证矩阵

| 改动区域 | 自动检查重点 | 实机重点 |
| --- | --- | --- |
| 解析／笔记事务 | 手改Markdown、多笔记、缺文件、损坏、保存失败、回滚、旧缓存 | 新建、追加、编辑、单条删除、侧栏与卡片一致、关闭重载 |
| 书籍状态／路径 | 身份、别名、改名移动、并发保存、失败恢复 | 打开与位置恢复、书签跳转、改名移动后来源返回 |
| 知识笔记 | 来源元数据、已有文件、重命名防重复、失败 | 提升后再打开、改名后再提升、删除独立笔记不删源片段 |
| 词条／翻译适配 | 单词短语边界、主动保存、外部失败不阻断、索引损坏 | 离线结果、词卡区别、明确触发翻译；不为清理默认发送请求 |
| 封面／统计管理 | 缓存、补录时长单位、聚合、删除保留边界 | 封面即时显示、补录与统计一致、菜单行为保持 |
| 生命周期／布局 | 订阅释放、异步失效、尺寸规则 | 反复切书、关闭、重载、侧栏伸缩、键盘与滚动 |
| 样式／构建 | 构建、语法、发布文件清单与敏感路径排除 | 已认可浅深主题、窄窗口、放大UI、长卡片效果不回退 |

实现批次必须运行npm run verify；仅文档任务检查链接、内容与diff即可。需要新增测试时验证行为与失败结果，不写重复实现的断言。测试使用内存或隔离临时素材；不得破坏真实文件制造故障。已有测试通过不代表未运行的实机闭环通过。

3. 每批任务记录：使用项目任务模板，写根因、范围、实现结果、验证与回滚。
4. 03／04：只写已完成事实和当前状态；02保留尚未完成优先级。

下一位执行者先完成阶段0、1、2，再交付首轮审查报告；其余阶段补齐后排序整改。可以分次审查，但每次要留下明确已查／未查边界。结束时对每条发现标记已验收、暂缓理由或待确认，不能以“整体代码更简洁”代替结论。

## 八、预计节奏与停止条件

按交付批次安排，不承诺未经调查的工期：第一轮建立基线与主流程图，第二轮完成数据、残留与参数证据，第三轮补齐生命周期／样式和整改排序；实施每次一个小批次。

遇到真实数据风险、版本或工作区归属不明、迁移无回退、证据不足或问题不可复现时，停止相关改动并转诊断，其他独立调查继续。全部已确认高风险问题关闭、计划内整改验收完成、剩余项有明确保留理由与后续任务，才算本轮结构治理完成。不是必须清零所有any、拆完所有大文件或删除所有历史代码。
