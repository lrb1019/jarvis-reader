## 三、必须先理解的架构

### `BookNoteService`

负责读取和操作每本书的 Markdown 读书笔记。新功能不得绕过它直接在界面层解析文本。

### `HighlightService`

负责高亮元数据及其查询。

### `HighlightTransactionService`

负责高亮相关写入事务、回滚和启动恢复。

### `BookStateService`

负责阅读位置和书籍运行状态。

### `KnowledgeNoteService`

负责将阅读片段提升为知识笔记，并通过来源身份查找已有文件。

### `CoverCacheService`

负责本地封面缓存。书架和详情页应优先使用缓存，不应反复从 EPUB 慢速读取。

### 设置保存队列

所有设置保存必须串行化，避免多个界面同时保存时相互覆盖。

## 五、数据位置

主要运行数据位于插件目录下：

```text
index/highlights.json
index/word-assets.json
logs/index-changes.jsonl
pending/highlights/
backups/conflicts/
backups/migrations/
data.json
```

职责：

- `highlights.json`：高亮定位元数据
- `word-assets.json`：词条资源元数据
- `index-changes.jsonl`：索引变更记录
- `pending/highlights/`：未完成高亮事务
- `backups/conflicts/`：冲突备份
- `backups/migrations/`：迁移备份
- `data.json`：插件设置和必要运行配置

用户内容仍以其指定目录内的 Markdown 读书笔记和知识笔记为准。

## 六、高亮字段权威矩阵

| 字段 | 唯一权威来源 | 说明 |
| --- | --- | --- |
| `id`、`blockId` | `index/highlights.json` | Markdown 块 ID 是同一身份的可定位投影 |
| 书籍路径、笔记路径、章节、CFI、颜色 | `index/highlights.json` | 用于 EPUB 定位和系统恢复 |
| 创建与更新时间 | `index/highlights.json` | Markdown 时间行是可读投影 |
| 原文、汇总笔记、单条笔记 | 书籍 Markdown | sidecar 不保存正文 |
| AI 内容和关联链接 | 书籍 Markdown | 冲突合并不得把正文重新塞回索引 |

完全丢失高亮索引后，可以从 Markdown 恢复内容，但不能仅凭 Markdown 恢复 CFI。

## 七、当前已知风险

### 1. 异常场景缺少完整人工验收

自动测试已有覆盖，但以下场景仍应在真实 vault 中正式验收：

- 文件不可写
- sidecar JSON 损坏
- 同一片段在多个界面同时修改
- Obsidian 同步引发的内容冲突

### 2. Markdown 格式兼容

`1.3.1` 已修复多行章节标题解析问题。后续修改解析器时必须同时验证：

- 单行中文标题
- 多行中文标题
- 英文标题
- 纯划线
- 一条笔记
- 多条笔记
- 关联

### 3. 工作区状态

2026-07-28 非发布同步范围包括：

- `main.js`
- `styles.css`
- `deploy-local.mjs`
- `src/library/LibraryApp.tsx`
- `src/workspace-navigation.ts`
- `tests/workspace-navigation.test.ts`
- `项目管理/03 改动日志.md`
- `项目管理/04 接续说明.md`
- `项目管理/06 发布与同步流程.md`

这些修复已经通过自动验证，部署到实际使用的 bylrb vault 完成运行验收，并已得到用户确认。此次只进行普通提交同步，不修改版本号、不创建标签或 Release。

本地实机验收使用 `npm run deploy:local`。实际 vault 路径保存在本机 Git 配置 `jarvis.runtimePluginDir` 中；该命令完整验证后只部署 `main.js` 和 `styles.css`，不接触用户数据。验收通过后以普通提交推送源码，只有正式发布才创建版本标签。

交付流程必须区分：

- **非发布同步**：小改动验收通过后，普通提交并推送 `main`；不修改版本号，不创建标签、发布包或 Release。
- **正式发布**：用户明确决定汇总累计改动后，才升级版本、创建版本标签、检查并公开 Release、执行 BRAT 验收。

普通提交是小改动的云端检查点。不得用临时标签标记小改动，也不得把普通推送授权解释为正式发布授权。

### 4. 大型文件与严格类型

阅读器、图书库和全局样式仍可能承担过多职责。严格类型门禁已覆盖数据安全核心模块，但不能假定整个项目已经完全消除 `any`。

### 5. 第三方智能指令

第三方插件桥接依赖非核心接口或界面结构，必须保持隔离。其失效不得阻塞阅读、笔记或保存。

## 九、下一位执行者的启动步骤

1. 只读取本目录的重建文档和当前源码。
2. 检查 `git status`，区分用户改动与任务改动。
3. 确认 `package.json`、`manifest.json` 和 Git 标签均为 `1.3.1`。
4. 运行 `npm run verify`。
5. 在真实 Obsidian 中建立最小测试书，验证纯划线和多笔记。
6. 若出现显示问题，先检查 Markdown 块，再检查 `BookNoteService` 解析结果，最后检查界面。
7. 不在三个界面分别增加兼容补丁。

## 十、禁止事项

- 不读取或覆盖用户未授权的其他项目文件。
- 不因单条异常数据增加永久兼容分支。
- 不让 JSON 索引替代 Markdown 内容。
- 不把每条划线拆成独立文件。
- 不删除孤立的读书笔记或知识笔记。
- 不直接修改已发布标签。
- 不在未运行完整验证时发布。

## 十一、推荐下一步
