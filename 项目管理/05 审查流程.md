# 审查流程

## 一、目标

审查的目的不是寻找更多功能，而是确认：

- 主工作流是否闭环
- 数据是否有唯一真相
- 多界面是否一致
- 删除和失败是否安全
- 发布后是否可安装、升级和回退

## 二、需求审查

每个需求先回答：

1. 它解决的是阅读、沉淀还是知识连接？
2. 用户在哪个具体动作中遇到问题？
3. 问题是数据错误、解析错误、状态不同步还是纯视觉问题？
4. 是否已有组件或服务可以解决？
5. 最小完整改动是什么？
6. 删除该功能是否影响核心工作流？

若需求不能改善核心工作流，进入后续想法，不立即实施。

## 三、任务类型

| 类型 | 默认行为 |
| --- | --- |
| 调研 | 只读，不修改 |
| 缺陷诊断 | 复现并定位根因 |
| 缺陷修复 | 最小修改并完整验证 |
| 功能开发 | 先定义完整生命周期 |
| 架构治理 | 收敛入口、数据或模块，不擅自改变用户行为 |
| 文档治理 | 修正规则和流程，不虚构代码事实 |
| 同步 | 提交并推送已有成果，不自动发布 |
| 发布 | 生成可安装版本，必须明确授权 |

## 四、任务卡

非简单任务开始前记录：

```markdown
任务名称：
任务类型：
用户场景：
当前现象：
复现步骤：
根因证据：
本次目标：
完成条件：
本次范围：
明确不做：
影响的数据和文件：
自动验证：
实机验证：
失败处理：
回滚方式：
需要更新的文档：
```

根因未确认时只能进入诊断阶段，不能把猜测直接写成修复方案。

## 五、根因检查顺序

出现“Markdown 正常但界面错误”时：

1. 检查实际 Markdown 块。
2. 检查块 ID 和章节边界。
3. 检查 `BookNoteService` 解析结果。
4. 检查 hydration 或索引路由。
5. 检查界面映射。
6. 最后才检查样式。

出现“保存后内容消失”时：

1. 检查写入事务结果。
2. 检查 Markdown 是否成功落盘。
3. 检查 sidecar 是否成功更新。
4. 检查回滚是否执行。
5. 检查界面是否使用旧缓存。

禁止通过调整 CSS 掩盖数据或解析错误。

## 六、代码审查

### 数据模型

- 原文、笔记、关联是否仍属于同一片段？
- 是否引入第二份内容真相？
- 身份是否依赖可修改名称？

### 服务边界

- 界面是否绕过 `BookNoteService`？
- 多个界面是否复制了解析代码？
- 写入是否进入事务和保存队列？

### 删除边界

- 删除单条笔记是否只影响目标笔记？
- 删除划线是否清理对应元数据？
- 删除书籍是否保留 Markdown 和知识笔记？

### 失败处理

- 写入失败是否可见？
- 原文件是否保留？
- 是否有备份和恢复路径？
- 启动时能否恢复未完成事务？

### 维护成本

- 是否为不可复现个例增加长期分支？
- 是否可以删除重复逻辑？
- 是否新增了没有测试的隐式格式？

## 七、自动验证

执行：

```bash
npm run verify
```

发布前还应执行：

```bash
npm run package:release
```

失败时不得跳过测试直接构建或发布。

## 八、人工验收矩阵

| 场景 | Markdown | 侧边栏 | 正文弹窗 | 详情页 |
| --- | --- | --- | --- | --- |
| 纯划线 | 原文完整 | 原文摘要 | 原文完整 | 原文完整 |
| 一条笔记 | 原文+笔记 | 原文+摘要 | 原文+笔记 | 原文+笔记 |
| 多条笔记 | 全部保存 | 数量/摘要 | 全部显示 | 全部显示 |
| 有关联 | 关联完整 | 可简化 | 全部显示 | 全部显示 |
| 删除一条笔记 | 仅目标消失 | 同步更新 | 同步更新 | 同步更新 |
| 删除划线 | 整块删除 | 消失 | 关闭/消失 | 消失 |

## 九、数据生命周期检查

每个受影响实体必须回答：

1. 首次创建后保存在哪里？
2. 关闭并重开后从哪里恢复？
3. 文件缺失时发生什么？
4. 文件损坏时发生什么？
5. 编辑由谁提交？
6. 删除清理哪些层？
7. 旧缓存是否会让数据复活？
8. 用户手工修改 Markdown 是否会被覆盖？

任何问题没有答案，任务不得放行。

## 十、异常验收

### 写入失败

- 将目标目录设置为不可写或模拟写入异常。
- 创建划线和笔记。
- 确认没有假成功。
- 恢复权限后确认可重试。

### sidecar 损坏

- 备份测试数据。
- 制造无效 JSON。
- 重启插件。
- 确认停止覆盖、保留原文件并产生诊断。

### 跨界面同步

- 同时打开阅读器和详情页。
- 新增、编辑、追加和删除笔记。
- 确认无需重启即可一致。

### 冲突

- 模拟 Markdown 外部修改与插件内修改。
- 确认生成冲突备份。
- 确认不会静默覆盖用户内容。

## 十一、界面验收

使用 13 英寸屏幕检查：

- 无横向溢出
- 长标题不会挤压按钮
- 词卡标签不会覆盖单词
- 操作图标位置一致
- 工具提示不重复
- 封面不拉伸、不补空白
- 封面缓存命中时快速显示
- 侧边栏卡片不会因无笔记而成为空壳

## 十二、结构审查

每完成三至五个功能任务，单独执行一次结构审查：

- 是否有多个界面直接修改同一主数据？
- 是否存在同名重复实现或失效文件？
- 是否有组件同时承担过多职责？
- 是否有字段被多个含义复用？
- 是否有临时补丁进入启动或保存主路径？
- 是否有文档规则与代码行为冲突？
- 是否有测试长期只覆盖纯函数？
- 是否有第三方私有接口渗入核心链路？

结构审查只生成明确任务，不在审查过程中顺手批量改代码。

## 十三、事故复盘

发生数据丢失、删除后复活、无法启动、发布包不可安装或连续三次失败时，必须记录：

```markdown
日期：
影响范围：
用户现象：
直接原因：
系统根因：
为什么现有测试没有发现：
恢复过程：
最终修复：
新增门禁：
```

稳定规则进入项目规则，完成事实进入改动日志，当前风险进入接续说明。

## 十四、结论格式

每轮审查必须给出：

- 已通过
- 未通过
- 未验证
- 风险
- 下一步

“没有发现问题”不等于“没有风险”。未覆盖的异常场景必须明确写为未验证。
