# 发布与同步流程

## 一、发布目标

Jarvis Reader 通过 GitHub Release 分发，并允许用户通过 Obsidian BRAT 插件安装和更新。

发布必须同时满足：

- GitHub 仓库代码可追溯
- Release 附件符合 Obsidian 插件格式
- 版本号一致
- BRAT 能识别并拉取

## 二、管理文档同步

正式管理文件位于实际使用的 iCloud 插件项目：

```text
AGENTS.md
项目管理/00 项目总览.md
项目管理/01 项目规则.md
项目管理/02 后续想法.md
项目管理/03 改动日志.md
项目管理/04 接续说明.md
项目管理/05 审查流程.md
项目管理/06 发布与同步流程.md
```

源码 Git 仓库保存同结构的无凭据镜像。每次提交管理文档前执行：

```bash
npm run sync:management
```

同步目录由本机 Git 配置提供：

```bash
git config --local jarvis.managementDir <实际插件项目根目录>
```

该路径只保存在 `.git/config`，不会上传 GitHub。

同步脚本只允许复制上述八份白名单文件，并在发现 GitHub 令牌、带凭据远端地址或缺失文件时停止。以下内容永远不参与管理文档同步：

- `.local-secrets/`
- `data.json`
- `index/`
- `logs/`
- `cache/`
- `pending/`
- `backups/`
- 用户书籍和笔记

GitHub 令牌只允许保存在系统凭据存储或被 Git 忽略的本机 `.local-secrets/`。不得写入 iCloud 管理文档、Git 镜像、发布说明或远端地址。

## 三、两类交付流程

必须区分“非发布同步”和“正式发布”：

| 项目 | 非发布同步 | 正式发布 |
| --- | --- | --- |
| 触发条件 | 单个小改动已自动验证并通过实际 vault 验收 | 用户明确决定汇总现有改动并发布 |
| Git 动作 | 普通提交并推送 `main` | 发布提交、推送 `main`、创建并推送版本标签 |
| 版本号 | 不修改 | 按发布范围升级并保持所有版本文件一致 |
| 标签 | 不创建任何标签 | 创建与包版本一致的 `*.*.*` 标签 |
| GitHub Release | 不创建、不触发 | 标签触发草稿 Release，检查后公开 |
| BRAT 用户 | 尚不能通过正式渠道获得该改动 | Release 公开并通过 BRAT 验收后可获得 |
| 目的 | 保存、追踪和云端同步已验收源码 | 向用户交付一批累计改动 |

普通提交就是小改动的云端检查点，不使用临时标签。推送普通提交不等于发布，也不构成创建版本标签或公开 Release 的授权。

### A. 小改动：本地验收后非发布同步

默认流程：

源码修改 → 自动验证和构建 → 部署到实际使用的本地 vault → 用户实机验收 → 普通提交并推送源码。

首次使用时，在源码仓库配置实际 vault 的插件目录：

```bash
git config --local jarvis.runtimePluginDir <实际 vault/.obsidian/plugins/jarvis-reader>
```

该路径只保存在 `.git/config`，不会上传 GitHub。配置完成后执行：

```bash
npm run deploy:local
```

该命令必须：

- 先运行完整的 `npm run verify`
- 校验源码与目标目录的插件 ID 均为 `jarvis-reader`
- 只部署构建生成的 `main.js`
- 通过目标目录内的临时文件进行替换
- 不复制或改动 `data.json`、索引、日志、缓存、备份、用户书籍和用户笔记

部署后重新加载 Jarvis Reader，并在实际 vault 中完成相关用户流程验收。验收通过后可以提交并推送源码，但不修改版本号、不创建标签、不触发 GitHub Release。

非发布同步前必须再次确认：

- 改动已经通过自动验证和对应实机验收
- 提交范围只包含本次已验收改动
- 改动日志和接续说明已更新
- 用户明确授权推送普通提交
- 没有修改版本号
- 没有创建标签、发布包或 Release

### B. 累计改动：统一正式发布

只有用户明确提出“发布”后才开始。默认流程：

确定累计改动范围 → 更新版本与发布说明 → 完整发布检查 → 构建发布包 → 提交并推送 → 创建版本标签 → 检查 GitHub Actions 草稿 → 用户确认后公开 Release → BRAT 验收。

此前对普通提交推送的授权不能自动延伸为版本标签或 Release 授权。正式发布继续执行下文全部门禁。

## 四、发布前检查

### 1. 工作区

```bash
git status --short
```

确认：

- 没有误包含用户数据
- 没有误包含本地缓存、日志或备份
- 没有覆盖不属于本次任务的改动
- 本次发布范围明确

### 2. 版本一致性

检查：

- `package.json`
- `package-lock.json`
- `manifest.json`
- `versions.json`
- `README.md`
- `README.en.md`

版本必须完全一致，例如 `1.3.1`。

### 3. 完整验证

```bash
npm ci
npm run verify
npm run package:release
```

必须确认：

- 类型检查通过
- 严格类型检查通过
- 测试通过
- 构建通过
- 发布包生成成功

## 五、发布包要求

GitHub Release 至少包含：

- `main.js`
- `manifest.json`
- `styles.css`
- 完整插件压缩包

如离线词典由发布包携带，还必须包含：

- ECDICT 分片资源
- `THIRD_PARTY_NOTICES.md`

压缩包根目录应直接包含插件运行文件，不得多套一层无关目录。

不得包含：

- `data.json`
- `index/`
- `pending/`
- `logs/`
- `backups/`
- 用户书籍
- 用户 Markdown 笔记
- 本地封面缓存
- 访问令牌、API 密钥或带凭据的远端地址

任何令牌都不得写入管理文档。GitHub 身份认证只能使用系统凭据存储、GitHub CLI 登录或受控环境变量。

## 六、Git 发布步骤

发布、推送和公开 Release 是外部动作，执行前必须得到明确授权。

### 1. 提交

```bash
git add <本次发布文件>
git commit -m "release: 1.3.2"
```

不得使用笼统的全量暂存掩盖无关文件。

### 2. 推送主分支

```bash
git push origin main
```

### 3. 创建并推送标签

```bash
git tag 1.3.2
git push origin 1.3.2
```

标签规则：

- 使用 `1.3.2`
- 不使用 `v1.3.2`
- 标签必须与 `package.json` 版本一致
- 已发布标签不得移动或复用

## 七、GitHub Actions

当前 Release 工作流在推送 `*.*.*` 标签时触发，并执行：

1. 使用 Node.js 24。
2. 安装锁定依赖。
3. 运行完整验证。
4. 生成发布包。
5. 校验标签版本等于包版本。
6. 创建 GitHub 草稿 Release。
7. 上传 `main.js`、`manifest.json`、`styles.css` 和压缩包。

若工作流失败：

- 不手工绕过失败直接发布。
- 先检查失败日志。
- 修复后发布新的补丁版本。
- 不删除并重建相同的公开标签。

## 八、发布草稿检查

公开 Release 前检查：

- 标题和标签一致
- 附件齐全
- `manifest.json` 版本正确
- `main.js` 为本次构建结果
- `styles.css` 存在
- 压缩包可以正常解压
- Release 说明列出用户可感知改动、数据迁移和已知风险

确认无误后再发布草稿。

## 九、BRAT 验收

### 新安装

1. 新建一个不含开发目录和旧插件数据的测试 vault。
2. 在 Obsidian 安装并启用 BRAT。
3. 添加 Jarvis Reader 的 GitHub 仓库地址。
4. 让 BRAT 拉取最新 Release。
5. 启用 Jarvis Reader。
6. 确认插件设置入口存在。
7. 确认离线词典和第三方许可随包可用。
8. 打开书架和一本测试 EPUB。

### 升级

1. 保留一份旧版测试 vault。
2. 通过 BRAT 更新到新版本。
3. 重载 Obsidian。
4. 检查设置、书架、封面、阅读位置和已有 Markdown。
5. 新建纯划线、一条笔记和多条笔记。
6. 检查侧边栏、正文弹窗和详情页一致。

### 必验功能

- 插件正常加载
- 设置齿轮存在
- 书籍详情页可打开
- 阅读位置恢复
- 划线原文显示
- 多条笔记显示和单条删除
- 书签跳转
- 知识笔记提升和重复打开
- 翻译卡与词卡
- 封面缓存

## 十、回退原则

如果新版本存在严重问题：

1. 保留故障版本和日志。
2. 不移动已发布标签。
3. 允许用户通过 BRAT 或手工附件安装上一个稳定版本。
4. 修复后发布新的补丁版本。
5. 若涉及数据格式迁移，必须先验证旧数据可读，再允许升级。

## 十一、发布完成记录

每次发布后在改动日志记录：

- 版本
- 标签
- 提交
- Actions 状态
- Release 状态
- BRAT 新装结果
- BRAT 升级结果
- 数据迁移结果
- 未验证项
