# Jarvis Reader 项目规则

## 一、决策顺序

所有改动必须按以下顺序进行：

理解需求 → 找到根因 → 确认数据边界 → 选择最小方案 → 实施 → 自动验证 → 人工验收 → 更新记录。

不得先改界面，再猜测底层数据。

## 二、内容规则

1. 每本书使用一份 Markdown 读书笔记。
2. 每个划线片段使用一个唯一块 ID。
3. 划线原文、笔记、关联属于同一个阅读片段。
4. 一处划线可以没有笔记，也可以有多条笔记。
5. 删除某条笔记只删除该笔记，不能删除划线原文、其他笔记或关联。
6. 章节标题用于定位，不是卡片的核心正文。
7. Markdown 是内容真相，JSON 索引只用于定位、检索和性能优化。
8. 不得让多个界面维护各自的内容解析规则。

## 三、数据权威关系

| 数据 | 权威来源 | 其他层的职责 |
| --- | --- | --- |
| 阅读设置、位置、进度、书签 | `data.json` 及对应状态服务 | 界面只提交操作，不直接修改存储对象 |
| 高亮标识、书籍路径、章节、CFI、颜色和系统时间 | `index/highlights.json` | Markdown 只保存同一块 ID 的可读投影 |
| 划线原文、完整笔记、关联和 AI 内容 | 书籍 Markdown 总笔记 | sidecar 不保存第二份正文 |
| 词义、来源、收藏和掌握状态 | `index/word-assets.json` | 各词汇界面通过统一服务访问 |
| 独立知识内容 | 独立 Markdown 笔记 | 来源元数据用于找回，不替代正文 |
| 索引变更记录 | `logs/index-changes.jsonl` | 只用于审计，不作为内容恢复源 |

同一字段只能有一个权威来源。缓存、摘要和界面投影不得反向覆盖权威数据。

## 四、高亮身份与写入规则

1. `cfiRange` 是 EPUB 原文定位依据，不得用视觉坐标或章节标题替代。
2. `id` 与 `blockId` 必须稳定，重载后不得重新生成。
3. Markdown 块末尾的块 ID 必须与索引中的块身份一致。
4. 创建、编辑、追加和删除必须通过统一服务。
5. Markdown 写入失败时不得继续提交索引。
6. 索引写入失败时必须回滚 Markdown，或留下可恢复事务。
7. 用户手工编辑 Markdown 后，不得由旧缓存静默覆盖。
8. 完全丢失 `highlights.json` 时，Markdown 可恢复内容，但无法凭空恢复 EPUB CFI；不得声称能够完整重建定位。

## 五、展示规则

### 侧边栏

- 纯划线必须显示划线原文，不得只显示时间或空卡片。
- 有笔记时仍要显示原文，并显示简短笔记摘要。
- 多条笔记以数量或紧凑摘要表达，不在侧边栏完整铺开。
- 点击卡片进入原文位置并按现有方式打开详细内容。

### 正文笔记弹窗

- 显示完整划线原文。
- 显示全部笔记。
- 显示全部关联。
- 点击输入框任意空白区域都应聚焦输入。

### 书籍详情页

- 显示完整划线原文。
- 一条、两条或多条笔记全部显示。
- 有关联时显示全部关联。
- 与侧边栏和正文弹窗使用同一解析结果。

### 翻译卡与词卡

- 临时翻译卡和已保存词卡可以视觉接近，但状态和功能必须清楚区分。
- 选中单词只显示一次，突出单词本身、发音和核心释义。
- 操作图标放在右上角，布局、间距和尺寸与已保存词卡一致。
- 工具提示只能有一套，不得同时出现浏览器原生提示与自定义提示。
- 窄屏优先显示单词、音标和释义；考试标签允许折叠或隐藏。

### 书籍封面

- 以书架现有封面卡片的实际比例为视觉基准。
- 使用 `object-fit: cover` 或等价方式保证不拉伸。
- 圆角必须裁在封面图片本身，不得用额外空白补高度。
- 详情页左右区域高度对齐时，应调整布局，不得压扁封面。
- 已缓存封面优先同步显示，避免先显示彩色占位卡再长时间替换。

## 六、知识笔记规则

1. 创建内容包括原文、全部笔记和来源链接。
2. 不自动生成无意义的标题正文块。
3. 默认文件名使用可识别且允许重命名的名称。
4. 查找已有知识笔记依赖来源元数据，不依赖文件名。
5. 已存在时直接打开，不重复新建。
6. 知识笔记目录属于设置项，不应每次创建时重复询问。

## 七、词汇与翻译规则

1. 离线查词不会自动创建词条，只有用户明确收藏才写入词库。
2. 单词、短语和句子类型必须明确，不得靠字段内容猜测。
3. 同一词条允许多个来源，来源必须保留书籍和原文定位。
4. `display` 是词卡正文显示源；摘要字段只能兜底。
5. 词汇界面必须通过统一词条服务读写，不得直接修改设置对象。
6. `word-assets.json` 缺失时创建当前版本的空文件，不从旧设置静默回填。
7. `word-assets.json` 损坏时停止加载和覆盖，明确提示并保留恢复材料。
8. 单词可以参与当前可视区域识别；短语和句子不得扫描整个仓库。
9. 单个英文单词优先使用内置离线词典。
10. 短语、句子或离线未命中内容，只能由用户明确触发 AI。
11. 外部请求只发送选中文本和必要上下文，不发送整章、整本书或无关笔记。
12. API 密钥不得写入日志、Markdown、Git、错误提示、示例或管理文档。
13. 第三方智能指令必须隔离在适配层，失效不得影响阅读和保存主链路。

## 八、删除规则

### 删除单条笔记

只删除目标笔记。

### 删除划线

必须明确告知会同时影响该划线下的笔记和关联，并执行一致性清理。

### 删除书籍

只删除书籍文件及其临时阅读状态。默认保留：

- 读书笔记 Markdown
- 已提升的知识笔记
- Obsidian 双链

### 删除或迁移索引

必须先备份，不得在校验失败时覆盖原文件。

所有真实删除、高影响覆盖和批量操作必须使用 Obsidian 风格确认界面，说明对象、数量、影响范围和是否可恢复。禁止使用浏览器原生 `confirm`、`alert` 代替正式交互。

## 九、架构规则

1. 界面层只展示状态和收集操作，不直接写主数据。
2. 服务层负责完整用户用例、写入顺序和失败处理。
3. 仓库与存储层负责 `data.json`、sidecar 和 Markdown 读写。
4. 领域纯逻辑不得直接访问 Obsidian、DOM、网络或文件系统。
5. 每个新实体必须定义创建、读取、更新、删除、重载、损坏和迁移生命周期。
6. 第三方私有对象、DOM 选择器和模拟点击必须隔离并记录风险。
7. 不进行一次性大重写；按用户闭环逐步迁移。

## 十、代码改动规则

1. 修改前阅读接口、调用方、共享工具和测试。
2. 优先修复共享服务，不在多个界面重复打补丁。
3. 优先删除重复逻辑，不新增没有明确职责的服务。
4. 所有持久化写入必须可失败、可回滚、可诊断。
5. 不直接编辑构建后的 `main.js` 作为长期方案。
6. 新增兼容逻辑必须有可复现样本和退出条件。
7. 无法复现的单条历史异常不进入主流程代码。
8. 不触碰与当前任务无关的用户改动。

## 十一、工程质量规则

1. TypeScript 新代码不得引入无边界 `any`。
2. `main.js` 只能由构建流程生成，禁止手工编辑。
3. 测试不得写入真实 `data.json`、`index/`、`logs/` 或用户 Markdown。
4. 异常大规模差异、整文件换行变化和来源不明修改必须先查明。
5. 临时文件只能使用约定前缀，并在任务结束前清理。
6. 重复实现只能保留一个真实入口。
7. 不得用“自动测试通过”替代 Obsidian 实机验收。
8. 连续三次无法定位同一问题时，必须收集 Obsidian 开发者工具日志。

## 十二、验证规则

每次提交前至少运行：

```bash
npm run verify
```

`verify` 必须覆盖：

- 类型检查
- 严格类型检查
- 自动测试
- 正式构建

涉及持久化时还要检查：

- 写入失败
- 索引损坏
- 临时文件恢复
- 重启恢复
- 跨界面同步
- 删除边界
- 关闭与重载
- 用户手工修改 Markdown
- 旧缓存是否导致删除数据复活

涉及界面时还要在 13 英寸屏幕下验收：

- 正常宽度
- 窄侧边栏
- 长文本
- 多笔记
- 无笔记
- 多标签

任务只有同时满足以下条件才算完成：

- 根因和目标明确
- 改动范围一致
- 数据生命周期完整
- 自动验证通过
- 对应实机验证通过
- 无异常差异和临时文件
- 文档与当前事实一致
- 回滚路径有效

## 十三、同步与发布规则

### 非发布同步

1. 单个小改动完成自动验证和实际 vault 验收后，可以用普通 Git 提交推送到 `main`。
2. 非发布同步只用于保存和共享已经验收的源码，不修改版本号，不创建任何标签、GitHub Release 或发布包。
3. 推送普通提交不等于发布，不得宣称 BRAT 用户已经获得该改动。
4. 普通 Git 提交就是小改动的云端检查点，不使用临时标签标记小改动。
5. 推送仍属于外部动作，必须得到明确授权。

### 正式发布

1. 只有用户明确决定汇总现有改动并发布时，才进入正式发布流程。
2. 发布前必须确定纳入范围，并确认工作区没有混入未验收改动或用户数据。
3. 版本号必须在 `package.json`、锁文件、`manifest.json` 和版本映射中一致。
4. 标签格式为 `1.3.1`，不使用 `v1.3.1`；标签版本必须等于包版本。
5. GitHub Actions 通过后先检查草稿 Release 的三个文件和压缩包。
6. 推送版本标签和公开 Release 属于外部动作，必须另行得到明确发布授权；此前对普通提交推送的授权不能替代发布授权。
7. 已发布版本不重新使用同一标签；修复必须发布新的补丁版本。

## 十四、文档规则

完成一个可交付改动后，至少更新：

- 改动日志
- 接续说明
- 验收状态
- 已知风险

文档只记录已确认事实。推测必须标注为“待验证”。
