# Jarvis Reader 项目总览

## 一、项目定位

Jarvis Reader 是运行在 Obsidian 中的 EPUB 阅读与知识沉淀插件。

它不是以“替代专业电子书阅读器”为第一目标，也不是以“背单词”为第一目标。它的核心价值是把读书过程变成 Obsidian 知识库的稳定输入端：

阅读原文 → 划线 → 写感想 → 建立关联 → 提升为知识笔记 → 回到知识库继续生长。

## 二、核心用户需求

1. 在 Obsidian 内直接阅读 EPUB，不离开当前知识环境。
2. 保存划线原文，并为同一处划线追加一条或多条笔记。
3. 让划线、笔记和 Obsidian 中已有文件形成双链。
4. 将有长期价值的阅读片段提升为独立知识笔记。
5. 阅读英文原著时，提供离线释义、发音、AI 翻译和可选的单词收藏。
6. 保持文件数量可控，不为每一条划线创建单独 Markdown 文件。

## 三、产品边界

### 核心能力

- EPUB 书架与阅读器
- 阅读位置恢复
- 划线、笔记、追加笔记和关联
- 书籍详情页、阅读侧边栏和正文弹窗的统一展示
- 书签保存与阅读界面内快速跳转
- 单词查询、翻译、收藏与复习
- 从阅读片段创建独立知识笔记
- 本地封面缓存与自定义封面
- 本地数据保护、冲突备份和异常恢复

### 次要能力

- 阅读统计
- 单词复习
- 智能指令
- AI 翻译

这些能力不能反过来挤占阅读和知识沉淀主流程。

### 明确不做

- 每条划线生成一个 Markdown 文件
- 为视觉效果保留低价值的 3D 书架或封面流
- 将考试标签、词频标签等低优先级信息塞满窄屏词卡
- 在没有真实需求前引入账号、云同步或复杂服务端
- 用特殊兼容代码长期掩盖无法复现的单条异常数据

## 四、核心工作流

### 1. 阅读输入

用户从指定书籍目录导入或打开 EPUB，插件恢复上次阅读位置。

### 2. 选中文本

选中文本后可执行复制、翻译、划线、写笔记或智能指令。

### 3. 内容落盘

每本书对应一份指定的 Markdown 读书笔记。每个阅读片段作为独立块写入，并带唯一块 ID。

一个片段应包含：

- 章节定位信息
- 划线原文
- 零条或多条个人笔记
- 零条或多条关联
- 时间
- 唯一块 ID

### 4. 多界面读取

阅读侧边栏、正文笔记弹窗和书籍详情页都应从同一内容模型读取，不得各自解释一套格式。

- 侧边栏：展示原文摘要、笔记摘要和笔记数量，保持紧凑。
- 正文弹窗：展示完整原文、全部笔记和全部关联。
- 详情页：展示完整原文、全部笔记和全部关联。

### 5. 知识提升

用户将有价值的片段提升为独立知识笔记时，内容必须包括：

- 划线原文
- 该片段的全部笔记
- 回到原书片段的来源链接

知识笔记通过稳定来源身份识别，而不是依赖文件名。用户重命名后再次点击，应打开已有文件，不得重复创建。

### 6. 后续回流

独立知识笔记进入 Obsidian 双链体系，与已有概念、项目和主题笔记连接，形成持续增长的知识库。

## 五、信息模型

### 内容真相

Markdown 是划线原文、笔记和关联的内容真相。

### 路由索引

`index/highlights.json` 只保存定位和路由元数据，不应成为正文内容的第二份真相。

### 运行状态

阅读位置、界面设置和其他运行状态由专门服务保存，不得与正文内容混写。

### 稳定身份

- 阅读片段：Markdown 块 ID
- 知识笔记：来源笔记路径与来源块 ID
- 书籍：稳定书籍标识及其文件路径

文件标题、章节标题和用户可修改名称都不能单独承担稳定身份。

## 七、数据安全原则

1. Markdown 内容优先于索引。
2. 索引写入必须校验并采用临时文件与备份替换。
3. 写入失败必须停止后续破坏性操作并保留恢复材料。
4. 删除书籍只删除书籍和临时阅读状态，不删除 Markdown 读书笔记或知识笔记。
5. 冲突、迁移和修复必须生成可追溯备份。
6. 不得把用户数据、缓存、日志和本地设置纳入发布包。

## 八、成功标准

- 新划线在 Markdown、侧边栏、正文弹窗和详情页中内容一致。
- 一处划线可追加多条笔记，删除单条笔记不会删除划线。
- 书签可在阅读界面快速查看和跳转。
- 阅读位置重启后可靠恢复。
- 知识笔记重复提升不会重复创建，重命名后仍可找回。
- 封面不拉伸、不补空白，并能从本地缓存快速显示。
- 异常写入不会破坏已有 Markdown 或索引。
- 发布包可通过 GitHub Release 和 BRAT 正常安装、升级和回退。

## 九、七份管理文档的职责

| 文档 | 唯一职责 |
| --- | --- |
| `00 项目总览` | 定义产品目标、边界、核心工作流和当前基线 |
| `01 项目规则` | 保存不可违反的长期规则 |
| `02 后续想法` | 只保存尚未完成且经过排序的事项 |
| `03 改动日志` | 保存已经完成并有证据的事实 |
| `04 接续说明` | 告诉下一位执行者当前状态、代码入口、风险和下一步 |
| `05 审查流程` | 定义从需求到验收、回滚和复盘的放行流程 |
| `06 发布与同步流程` | 定义提交、GitHub Release 和 BRAT 验收 |

临时分析、审计草稿和一次性计划不得长期混入七份核心文档。

## 十、管理信息与代码事实

项目协作必须同时检查两类信息：

### 管理信息

用于确认产品目标、长期规则、历史决策、当前风险和任务边界。

### 代码事实

用于确认真实入口、调用链、数据落点、构建脚本、测试和当前行为。

两者不是替代关系。正确顺序是：

管理文档确定方向 → 当前源码验证事实 → 实施和验收 → 回写管理文档。

当文档与代码冲突时，不能默认任何一方正确。必须先确认：

- 文档是否已经过期
- 代码是否发生回归
- GitHub 最新发布版本的实际行为
- 用户在 Obsidian 中的实机结果

## 十一、每次任务的文档使用顺序

1. 阅读项目总览、项目规则和接续说明。
2. 检查 Git 状态和当前版本。
3. 从后续想法或用户现场问题建立单一任务。
4. 按审查流程完成诊断、修改和验收。
5. 将完成事实写入改动日志。
6. 更新接续说明中的状态、风险和下一步。
7. 只有长期规则发生变化时才更新项目规则。
